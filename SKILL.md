# wiki-builder

A skill for building and maintaining a personal markdown knowledge base from raw source material. The design borrows the parts of Wikipedia's architecture that actually do useful work — namespace separation, lead-first articles, inline citations, aliases, disambiguation, derived backlinks — and drops the parts that don't fit a single-author, LLM-assisted workflow.

## Core philosophy

A wiki built this way has three jobs, in priority order:

1. **Faithful index of sources.** Every non-trivial claim must be traceable back to a specific source file. The wiki is not a place for the LLM to freelance — it is a place to organize what real sources actually say. Hallucinated content is worse than no content.
2. **High-density retrieval surface.** The user (and future LLM sessions) should land on any concept file and immediately get oriented. This is what the lead-first rule is for.
3. **Low-maintenance growth.** Structure must survive the wiki growing from 10 to 1000 files without manual rework. This is why backlinks are derived, categories are tags rather than folders, and the directory layout is deliberately shallow.

When these three goals conflict, faithfulness wins.

## Wiki layout

A wiki built with this skill lives in a single root directory and has this structure:

```
my-wiki/
├── AGENTS.md              # canonical agent instructions: retrieval protocol + wiki conventions
├── CLAUDE.md              # one-line stub routing Claude Code to AGENTS.md
├── index.md               # portal page — hand-maintained navigation aid
├── concepts/              # the main namespace — one file per concept
│   ├── transformer-ml.md
│   ├── prediction-powered-inference.md
│   └── ...
├── sources/               # one file per ingested raw source
│   ├── vaswani-2017-attention.md
│   ├── angelopoulos-2023-ppi.md
│   └── ...
├── meta/                  # "talk pages" — editorial notes, open questions
│   ├── transformer-ml.md  # mirrors concepts/transformer-ml.md
│   └── ...
├── disambig/              # disambiguation pages for ambiguous terms
│   └── transformer.md
├── raw/                   # untouched original files (PDFs, HTML dumps, images)
│   └── ...
├── scripts/               # copies of the helper scripts from this skill
└── indices/               # generated by scripts, never hand-edited
    ├── aliases.json
    ├── backlinks.json
    ├── orphans.json
    └── unused_claims.json
```

The four content namespaces (`concepts/`, `sources/`, `meta/`, `disambig/`) are flat — no nested subdirectories. Categorization happens via `tags` in frontmatter, not via folder hierarchy. This is the single most important structural decision: **folders are for namespaces, tags are for topics**. Wikipedia learned this the hard way; do not relitigate it.

`raw/` is sacred. Nothing in `raw/` is ever modified. When ingesting a PDF or HTML file, copy it into `raw/` and create a corresponding file in `sources/` that summarizes and indexes it. The source file points to the raw file; the raw file is the ground truth. Optionally, maintain a `raw/_queue.md` listing sources downloaded but not yet ingested — automated loops check this file each run to decide whether to ingest new material.

`indices/` is generated by the helper scripts in `scripts/`. Never hand-edit anything in there — it will be overwritten on the next run.

`index.md` is the wiki's **portal page** — see the dedicated section below.

## The portal page (`index.md`)

Every wiki has a single hand-maintained `index.md` at its root. It is the file a human reader (or future LLM session) opens first to orient themselves and to find concept articles. Think of it as the wiki's main page in the Wikipedia sense: a curated landing page that groups concepts the way a reader would naturally look for them, not the way the filesystem stores them.

Three properties make `index.md` distinct from concept articles:

1. **It lives at the wiki root, not under a namespace.** This is deliberate. The maintenance scripts (`build_alias_index.py`, `build_backlinks.py`, `check_links.py`) only scan the four content namespaces (`concepts/`, `sources/`, `meta/`, `disambig/`), so wikilinks inside `index.md` do **not** contribute to `backlinks.json`. That keeps the backlinks index clean: it shows real cross-references between content pages, not the portal's enumeration of every concept. The trade-off is that `check_links.py` will not catch broken wikilinks in the portal — you need to maintain it carefully by hand.
2. **It is hand-maintained, not derived.** Auto-generating it from `concepts/` would technically work but would defeat its purpose: the value of a portal is editorial judgment about what to highlight, how to group, and what order to present things in. A flat alphabetical listing of every concept file is the failure mode, not the goal.
3. **It uses `[[wikilink]]` syntax.** In Obsidian and similar viewers the links become clickable; in plain text editors they remain readable.

The bootstrap script scaffolds `index.md` from `assets/index.template.md` with placeholder sections for "Start here", "Concepts by topic", "Sources", "Frontier (red links)", and "About this wiki". After bootstrapping, fill these in as the wiki grows. **Update the portal whenever you add a major concept or finish a thematic cluster** — a stale portal is worse than no portal.

When the wiki is small (under ~5 concepts) the portal is barely useful and can be ignored. Once it crosses ~10 concepts the portal starts being the fastest way for a reader to find anything, and it should be kept current from then on.

### Index table schemas

The portal's concept list and source list are markdown tables, and their column schema is **not** one-size-fits-all — it should follow the shape of the material. Default to `Concept | Short description` for the concept table and pick the source table by corpus type (`Source file | Topic` for whole books, `Source file | Scope indexed` for partial ingestion, `Source file | Chapter | Covers` for chapter-split sources, `Source | Topic | Year` for a paper corpus). The governing rule is that a column earns its place only if it is filled for most rows and isn't already in frontmatter — so don't duplicate `tags`/`status`, and don't add a cross-source "Key distinction" column unless the wiki was built to compare sources. **See `references/index_schema_design.md`** for the full decision guide, the optional-column triggers, formatting rules (compact delimiters, pipe-escaping in cells), and worked examples — read it whenever you are designing or revising a portal's tables.

## Frontmatter schemas

Every file in `concepts/`, `sources/`, and `disambig/` has YAML frontmatter. The schemas are minimal but strict. See `references/frontmatter_schema.md` for the full specification; the short version is:

**concepts/*.md**

```yaml
---
id: prediction-powered-inference     # must match filename stem
title: Prediction-Powered Inference
aliases: [PPI, prediction powered inference]
tags: [statistics, semi-supervised, inference]
status: stub                          # stub | draft | stable
created: 2026-04-07
updated: 2026-04-07
sources: [angelopoulos-2023-ppi]
---
```

**sources/*.md**

```yaml
---
id: angelopoulos-2023-ppi
title: "Prediction-Powered Inference"
authors: [Angelopoulos, Bates, Fannjiang, Jordan, Zrnic]
year: 2023
kind: paper                           # paper|article|repo|dataset|video|conversation|other
url: https://arxiv.org/abs/2301.09633
raw: raw/angelopoulos-2023-ppi.pdf
ingested: 2026-04-07
---
```

**disambig/*.md**

```yaml
---
id: transformer
kind: disambiguation
---
```

The `id` field must always equal the filename stem. This is what makes link checking and backlink generation reliable.

## Writing rules for concept articles

These rules exist because skipping any of them is what historically turns an LLM-maintained wiki into a pile of mush. Each has a reason attached — internalize the why and the rule stops feeling arbitrary. When a real edge case comes up, let the reasoning (not the letter of the rule) guide the call.

### 1. Lead-first

Every concept article opens with a **lead section**: 2–4 sentences, no heading, that must be independently understandable. A reader who only reads the lead should walk away knowing what the concept is, why it matters, and roughly how it relates to neighboring concepts. The first sentence should be a definition with the concept name in bold.

Example:

```markdown
**Prediction-powered inference (PPI)** is a statistical framework that combines a small
labeled dataset with a large pool of machine-learning predictions to produce confidence
intervals and p-values that remain valid even when the ML model is biased[^1]. It targets
the common research situation where labels are expensive but predictions are cheap, and
is closely related to [[semi-supervised-learning|semi-supervised inference]] and
[[debiased-machine-learning]].

… body of the article …

## Notes

[^1]: [[angelopoulos-2023-ppi#^thm-1|Angelopoulos 2023, §thm-1]]
```

Notice three things about that citation:

1. **In the body it's a footnote reference** (`[^1]`), flush against the cited word, no leading space — the same convention Wikipedia and printed books use. Obsidian renders `[^1]` as a small superscript that is clickable; clicking it jumps to the matching `[^1]:` definition in the Notes section at the bottom of the page, and clicking the back-arrow returns the reader to where they were.
2. **The actual source link lives in the Notes section**, not in the body. The Notes entry contains a clickable Obsidian block-reference wikilink to the cited claim in the source file, with display text in `Author Year, §anchor` form so the reader sees at a glance what each note points to. Click-through from the body to the source is therefore two clicks (body → Notes → source), which matches Wikipedia's UX exactly.
3. **The display text in the Notes entry is derived mechanically** from the source-id `<lastname>-<year>-<slug>` → `Lastname Year`. When two sources share the same author and year, disambiguate with `a`/`b` suffixes (e.g. `Gou 2025a`, `Gou 2025b`). Per-file footnote numbering — each concept article restarts at `[^1]`, like a Wikipedia article.

After the lead, use `## H2` headings for the body. A common structure for a concept article is Definition → Intuition → Formal statement → Variants → Relationship to other concepts → Open questions. Adapt as needed; this is a guideline, not a template.

### 2. Inline citations are mandatory for non-trivial claims

Every claim that isn't either (a) a direct definition of the concept or (b) common knowledge in the field must have an inline citation pointing to a file in `sources/`. Citations follow the **Wikipedia / academic-paper convention**: a numbered footnote reference in the body, with the actual source link living in a `## Notes` section at the bottom of the file.

```markdown
… some claim that needs a citation[^1]. Another claim that uses the same source[^1].
A third claim, different paper[^2].

… rest of the article …

## Notes

[^1]: [[angelopoulos-2023-ppi#^thm-1|Angelopoulos 2023, §thm-1]]
[^2]: [[zhu-2023-phasenet-das#^sec-methods-architecture|Zhu 2023, §sec-methods-architecture]]
```

Three rules for how to write citations correctly:

1. **In the body, use markdown footnote references `[^N]`.** Per-file numbering — each concept article restarts at `[^1]`. The reference is flush against the cited word with no leading space (like Wikipedia: `… 21 July 2022[^1].`). Same target reused in the body → same number; a different anchor of the same source → a different number.
2. **Each `[^N]` must have a matching `[^N]:` definition in the `## Notes` section at the bottom of the file.** The Notes entry is the actual source citation: an Obsidian block-reference wikilink of the form `[[source-id#^anchor|Author Year, §anchor]]`. The stem must match a real `sources/<source-id>.md`, and the `^anchor` must match a block ID inside that source file's "Key claims" bullets — see "Source file structure" below. This is the link that `check_links.py` validates: an unresolved source wikilink anywhere in the file (Notes section included) is a hard error and exits non-zero, because it almost always means the LLM hallucinated a source.
3. **The display text in each Notes entry is derived mechanically** from the source-id `<lastname>-<year>-<slug>` → `Lastname Year, §anchor`. Same-author-same-year collisions get `a`/`b`/`c` suffixes ordered alphabetically by full source-id (e.g. `gou-2025-depic` → `Gou 2025a`, `gou-2025-monterey-eew` → `Gou 2025b`). Keeping this mechanical means future LLM sessions don't have to invent display text by hand.

**Concept-to-concept wikilinks** use plain `[[concept-id]]` form (no `^` block reference, no `[^N]` footnote wrapping). They appear inline in the body and resolve through the alias index. `check_links.py` distinguishes the two kinds by whether the wikilink target stem matches a file in `sources/` or a concept in the alias index.

**Why this convention?** Three reasons:

- **Compact in the body.** A `[^1]` superscript reads as a tiny visual mark in prose, exactly like a printed-book footnote. A long inline wikilink like `[[romanowicz-2023-seafoam#^sec-setup|Romanowicz 2023, §sec-setup]]` is technically valid but visually heavy; readers (and you, when re-reading) scan past such citations more easily as numbered marks.
- **All source links collected in one place.** When auditing whether a concept article is well-sourced, scrolling to the bottom and reading the Notes section is the fastest way to see exactly which sources back the article and where each goes. This is why printed books and Wikipedia both do it.
- **Table cells just work.** A `[^N]` reference inside a markdown table cell needs no escaping, unlike a raw `[[stem|alias]]` wikilink which has to be written as `[[stem\|alias]]` to avoid being misparsed as a column separator. Footnotes sidestep that whole problem.

If you find yourself wanting to write something you can't cite, **stop**. Either find a source for it (and add it to `sources/`), or move the claim into the corresponding `meta/` file as an open question, or omit it. Never paper over a missing citation with hedging like "it is generally believed that...".

### 3. Wikilinks for cross-references

Use `[[concept-id]]` or `[[concept-id|display text]]` to link to other concept articles. The id must either match a file in `concepts/` directly or match an alias listed in some concept's frontmatter. Link the **first** mention of a concept in an article, not every mention.

```
PPI is closely related to [[semi-supervised-learning|semi-supervised inference]]
and to [[debiased-machine-learning]].
```

If a wikilink target doesn't exist yet, that's fine — it becomes a "red link" and shows up in `indices/orphans.json` as a hint for what to write next. Red links are a feature: they tell you where the wiki's frontier is.

**Wikilink policy for sustainable growth.** A good concept article should produce 3–8 outbound wikilinks, of which at least 2–3 may be red links to concepts not yet written. If you finish writing a concept and it has zero red links, you are probably being too conservative — go back and add links to related concepts that a reader would reasonably want to look up. Do NOT avoid red links to "keep things clean." A wiki with no red links is a wiki that has stopped growing. Add this policy to your wiki's `AGENTS.md` so that automated and future sessions follow it too.

### 4. No backlinks section in the file itself

Do not write a "Backlinks" or "Referenced by" section by hand. Backlinks are computed by `scripts/build_backlinks.py` and stored in `indices/backlinks.json`. If the user wants to see what links to a concept, run the script and read the index. Hand-maintained backlink sections always rot.

### 5. Aliases live in frontmatter, not in redirect files

Wikipedia uses dedicated redirect pages because MediaWiki has no other mechanism. We have YAML frontmatter, so we put aliases directly in the concept file. The `build_alias_index.py` script then produces `indices/aliases.json` mapping every alias to its canonical id. A wikilink like `[[PPI]]` resolves correctly via the alias index without needing a separate `PPI.md` redirect file.

### 6. Disambiguation when a term has multiple meanings

If a single term legitimately maps to multiple concepts (e.g. "Transformer" = ML architecture vs electrical device), do this:

- Create concept files with disambiguating slugs: `concepts/transformer-ml.md`, `concepts/transformer-electrical.md`.
- Create a disambiguation page at `disambig/transformer.md` that lists the alternatives.
- Do **not** put `transformer` (unqualified) as an alias in either concept file — that would create an ambiguous resolution.

```markdown
---
id: transformer
kind: disambiguation
---

**Transformer** may refer to:

- [[transformer-ml]] — the neural network architecture introduced by Vaswani et al. (2017)
- [[transformer-electrical]] — the electrical device for changing voltage
```

### 7. Math notation conventions

**All mathematical notation must be written in LaTeX, never in Unicode.** Do not use Unicode Greek letters (α, β, θ), Unicode operators (≥, ≤, ∈, ∑, ∏), Unicode subscripts/superscripts (₁, ₂, ⁿ), Unicode arrows (→, ←), or Unicode accented characters (μ̂, x̄) anywhere in the wiki — not in concept articles, not in source files, not in portal pages or tables. Every piece of math, no matter how small, must be wrapped in LaTeX delimiters (`$...$` or `$$...$$`). The reason is simple: Unicode math doesn't render in Obsidian's MathJax, it drifts inconsistently across files, and it makes programmatic convention checking impossible.

Any concept article that contains mathematical notation must also follow the conventions in `references/math_conventions.md`. The short version:

- **Renderer target is Obsidian with MathJax 3** — no KaTeX, no custom preamble, no external LaTeX packages.
- **Delimiters**: inline `$ ... $` (never `\( \)`), display `$$ ... $$` on its own paragraph with blank lines above and below, multi-line via `$$\begin{aligned}...\end{aligned}$$` (never bare `align`).
- **Reference style is Wasserman, _All of Statistics_** — `\mathbb{P}`, `\mathbb{E}`, `\mathrm{Var}`, random variables in capital italic, estimators with hats, convergence in distribution via `\rightsquigarrow`.
- **Vectors and matrices are bold** (`\mathbf{x}`, `\mathbf{A}`) to match ML convention; transpose is `^\top`, norms use `\|`, inner products use `\langle \cdot, \cdot \rangle`.
- **Operators**: `\operatorname*{arg\,max}` (not `\arg\max`), `D_{\mathrm{KL}}(p \,\|\, q)` (not `KL(p||q)`), `\mathrm{tr}` (not `\text{tr}`).
- **Inline fractions**: use `1/2` inline, reserve `\frac` for display math.
- **Default to fixed-size brackets**; reach for `\left( \right)` only when contents are genuinely tall.

Before writing a math-heavy article, **read `references/math_examples.md`** — it contains 10 worked golden-reference examples (sample mean, CLT, multi-line derivation, estimator with hat, loss function, hypothesis test, optimization, measure theory, inline prose, proof sketch). Imitate the structural pattern of the closest example. The examples file is the "show, don't tell" companion to the conventions — when in doubt, match the examples rather than improvising.

The guiding question is always: **"Would Wasserman write it this way?"** A consistently slightly-suboptimal notation is better than a randomly-mixed "best" notation.

## Source file structure

Source files are short. Their job is to be a faithful, structured handle on a raw document — not to replace reading it. A source file should contain:

1. **Frontmatter** (see schema above).
2. **One-paragraph summary** of what the source is and what its main contribution is.
3. **Key claims** — a bullet list of the 3–10 most important specific claims. Each bullet starts with a bold short label (the anchor name) and ends with an Obsidian block ID `^anchor-name` so the bullet is clickable from a citation.
4. **Notes** (optional) — anything noticed when ingesting it that's worth preserving but isn't a claim.

```markdown
---
id: angelopoulos-2023-ppi
title: "Prediction-Powered Inference"
authors: [Angelopoulos, Bates, Fannjiang, Jordan, Zrnic]
year: 2023
kind: paper
url: https://arxiv.org/abs/2301.09633
raw: raw/angelopoulos-2023-ppi.pdf
ingested: 2026-04-07
---

Introduces prediction-powered inference, a framework for valid statistical inference
that uses a small labeled dataset to debias estimates derived from a large pool of
ML predictions.

## Key claims

- **thm-1**: The PPI confidence interval has valid coverage regardless of the ML
  model's accuracy, as long as the labeled sample is iid. ^thm-1
- **sec-3.2**: Width of the PPI interval scales with the rectifier variance, which
  shrinks as the ML model becomes more accurate. ^sec-3.2
- **sec-5**: Empirical evaluation on five datasets shows tighter intervals than the
  classical estimator using only labeled data. ^sec-5
```

Two things to notice in the example:

1. **The bold label and the block ID match.** The bold prefix `**thm-1**` is for visual scanning when reading the source file directly; the trailing `^thm-1` is the actual Obsidian block ID that citations resolve against. Keep them identical so a reader scanning the bullets knows exactly what each citation key refers to.
2. **The anchor names are arbitrary slugs.** `thm-1`, `sec-3.2`, `fig-4`, `abstract`, `table-1` — pick whatever makes the location unambiguous. They are what `[[angelopoulos-2023-ppi#^thm-1]]` block-reference citations resolve to in Obsidian.

For multi-line bullets (e.g. a parent bullet that contains nested sub-bullets), put the `^anchor` on the parent line, not on the last sub-bullet. Obsidian will scroll to the parent line when the link is clicked, with the sub-bullets visible just below.

## Workflow: ingesting a new source

When the user hands you a new source (a PDF, an article URL, a conversation transcript, etc.) and asks to add it to the wiki:

1. **Place the raw file.** Copy it into `raw/` with a stable slug-style name (e.g. `raw/angelopoulos-2023-ppi.pdf`). If the source is a URL, fetch it and save the content; do not rely on the URL staying alive.
2. **Read the source.** Actually read it — don't skim. Identify the main contribution and the 3–10 most important specific claims with their locations.
3. **Create the source file.** Write `sources/<id>.md` following the schema and template above.
4. **Identify which concepts it touches.** For each concept the source is relevant to:
   - If `concepts/<concept-id>.md` exists, update it: add the source to its `sources` frontmatter list, weave any new claims into the body with proper inline citations, and bump `updated`.
   - If it doesn't exist, decide whether to create it now or leave it as a red link. Default to creating it only if the source gives you enough material for at least a lead + one body section.
5. **Run the link check.** `python scripts/check_links.py <wiki-root>` to verify all citations and wikilinks resolve.
6. **Rebuild the indices.** `python scripts/build_alias_index.py <wiki-root>` then `python scripts/build_backlinks.py <wiki-root>`.

Stay in the loop. Do not auto-ingest batches of sources without the user confirming each one — the LLM's classification choices will drift, and errors compound.

## Workflow: creating or updating a concept

1. **Check for existing files.** Look for `concepts/<id>.md` and any aliases that might already resolve. Don't create duplicates.
2. **Check for ambiguity.** If the term has multiple legitimate meanings in the user's domain, set up disambiguation before writing.
3. **Gather sources first.** Look in `sources/` for anything relevant. If there's nothing, ask the user whether to ingest sources first or write a stub from general knowledge marked `status: stub`.
4. **Write the lead first.** Get the 2–4 sentence lead right before writing anything else. If you can't write a clean lead, you don't understand the concept well enough yet.
5. **Body sections with inline citations.** Every non-trivial claim cited.
6. **Update frontmatter.** `aliases`, `tags`, `sources`, `updated` date.
7. **Run `check_links.py` and rebuild indices.**

## Workflow: testing a wiki

A wiki that passes `check_links.py` is structurally sound, but that doesn't mean it's actually *usable* — an LLM (or a human) trying to answer questions from the wiki may still fail because of missing cross-references, under-developed concept articles, weak `AGENTS.md` guidance, or the LLM silently falling back on its training data instead of the wiki's content. The retrieval test workflow catches these problems.

See `references/test_checklist.md` for the full checklist with detailed pass criteria and failure modes. What follows is the framework and when to use it.

### When to test

- **After completing a new wiki** (all sources ingested, concepts written, indices built). This is the most important time — run a full test before considering the wiki "done".
- **After restructuring** an existing wiki or making significant changes to `AGENTS.md` — re-run previously failing questions plus at least one boundary question.
- **As the wiki grows past ~100 concepts** — re-run structural questions, because grep-based fallbacks that worked at small scale start failing at this size.
- **Quarterly**, as a sanity check — pick 3 random questions across all tiers to catch rot.

### The three-tier framework

Tests are organized into three tiers of increasing difficulty. Each tier targets a different class of failure:

**Tier 1 — Lookup (sanity check).** Simple questions like "What is X?" or "Which paper proposed X?" that verify the basics: lead-first format is followed, frontmatter is parseable, cross-file comparison works. If these fail, something fundamental is broken. All Tier 1 questions should pass before moving to Tier 2.

**Tier 2 — Structural (stress test).** Questions that probe whether the AI uses the wiki's structural features — indices, backlinks, wikilinks — or falls back on brute-force grep. Examples: "How many sources mention X?" (tests index usage), three-hop traversals (tests backlink navigation), claim-level sourcing (tests citation granularity), and frontier questions (tests awareness of `orphans.json`). This is where most wikis reveal their weaknesses.

**Tier 3 — Boundary (most important).** Tests whether the wiki has become the AI's actual knowledge boundary, or whether the AI silently fills gaps from training data. Three key tests:
- **"I don't know" test** — ask about something plausibly in-domain but absent from the wiki. The AI must say it doesn't know, not confabulate.
- **Contradiction test** — ask whether any sources disagree. The AI must actually check, not assume agreement.
- **Fabricated-citation test** — after the AI cites a source, ask it to show the exact passage. The citation must be real, not decorative.

Run at least one Tier 3 question in every test session. These catch the failures that matter most.

### Classifying failures

After testing, classify each failure to determine what to fix:

| Category | Symptom | Fix |
|----------|---------|-----|
| **Content gap** | The wiki genuinely lacks the information | Write more concepts or ingest more sources |
| **Structural gap** | Information exists but the AI couldn't find it efficiently | Add wikilinks, fix aliases, rebuild backlinks |
| **AGENTS.md gap** | Structure exists but the AI didn't know to use it | Update the retrieval playbook in `AGENTS.md` |
| **Tooling gap** | A missing index or check would have caught this | Consider a new helper script |

The exploration trace — which files the AI opened and in what order — is more diagnostic than the final answer. Record it.

## Helper scripts

Three scripts live in `scripts/` and should be run after any non-trivial edit. They are deliberately simple, dependency-free (stdlib only), and do not modify content files — they only read content and write to `indices/`.

- **`build_alias_index.py <wiki-root>`** — reads `id` and `aliases` frontmatter from all concept files and produces `indices/aliases.json` mapping each normalized alias (and the canonical id itself) to the canonical id. Errors out non-zero on conflicts.
- **`build_backlinks.py <wiki-root>`** — scans every `.md` file under `concepts/`, `sources/`, `meta/`, `disambig/` for `[[wikilinks]]`, resolves concept-to-concept links through the alias index, and writes `indices/backlinks.json` (concept_id → list of files linking to it) and `indices/orphans.json` (unresolved concept links). **Source citations (block-reference form `[[X#^Y]]`, or bare `[[X]]` where X is a source filename) are deliberately excluded from both indices** — they are validated separately by `check_links.py` and would otherwise create noise in the concept backlink view.
- **`check_links.py <wiki-root>`** — validates every `[[wikilink]]`, classifying each into one of two kinds: a **source citation** (block-reference form `[[X#^Y]]`, or bare `[[X]]` where X matches a file in `sources/`) or a **concept link** (everything else). Source citations must resolve to a real `sources/<X>.md` file — an unresolved citation is a hard error and exits non-zero, because it almost always means the LLM hallucinated a source. Concept links are resolved through the alias index; red concept links are reported as warnings only (they're a feature — see `orphans.json`). Wire this into a pre-commit hook to catch hallucinations before they enter the wiki.

**Run order matters.** Always run `build_alias_index.py` first, because the other two depend on `indices/aliases.json`.

**Code spans are ignored.** Both `build_backlinks.py` and `check_links.py` strip fenced code blocks and inline `` `code` `` spans before scanning, so syntax examples like `` `[[Target]]` `` and `` `[[foo#^bar]]` `` inside backticks won't be counted as real references. This means meta-articles about wiki syntax don't generate spurious red links.

- **`unused_claims.py <wiki-root>`** — scans every `sources/*.md` file for block-id anchors (`^anchor-name`), cross-references against all `[[source-id#^anchor]]` citations in `concepts/`, `meta/`, and `disambig/`, and writes `indices/unused_claims.json` listing source anchors that no concept article cites. This is the **supply-side growth engine** — it surfaces ingested material that hasn't been synthesized into concept articles yet. Run it after `check_links.py` in the maintenance sequence. The JSON output groups unused claims by source with utilization percentages, making it easy for automated loops to prioritize under-utilized sources.

**Run order matters.** Always run `build_alias_index.py` first, then `build_backlinks.py`, then `check_links.py`, then `unused_claims.py`.

These four scripts are what the wiki keeps for ongoing maintenance. A fifth script, `bootstrap_wiki.py`, lives alongside them in the skill but is not copied into the wiki — it's a one-shot setup tool used only when creating a new wiki (see "Bootstrapping a new wiki" below). The four maintenance scripts get copied into `<wiki-root>/scripts/` automatically by `bootstrap_wiki.py` so the wiki is self-contained and version-controllable independently of this skill.

## Sustainable growth: four engines

A wiki that relies solely on `orphans.json` (red links) for its growth queue will stall at 20–30 concepts — each new article resolves existing red links but generates few new ones, especially if the LLM avoids red links to "keep things clean." The fix is to run four complementary growth engines, not one.

### Engine 1 — Red links (`orphans.json`)

Existing concept articles reference concepts that don't exist yet. This queue is self-consuming: it depletes as you write concepts and is replenished only if new concepts generate new red links. The wikilink policy (see "Wikilinks for cross-references" above) is the fix for depletion — enforce it in `AGENTS.md`.

### Engine 2 — Unused claims (`unused_claims.json`)

Source files contain key claims (with `^block-id` anchors) that no concept article cites. This queue is proportional to ingested source material and never depletes as long as you keep ingesting new sources. Run `scripts/unused_claims.py` to surface these. When unused claims exist, either write a new concept that cites them, or weave them into an existing concept article.

### Engine 3 — New source ingestion (`raw/_queue.md`)

Adding new papers, chapters, or datasets to `raw/` and building corresponding source files is the fundamental fuel. Without new sources, all other engines eventually converge. With new sources, all other engines are replenished. Optionally maintain a `raw/_queue.md` file listing sources downloaded but not yet ingested — automated loops check this file each run.

### Engine 4 — Quality deepening

Upgrading `status: stub` articles to `draft` or `stable`, adding second-source perspectives, filling in meta decision logs. This engine does not create new concepts but increases the value of existing ones. Prioritize stubs with high inbound-link counts (from `backlinks.json`).

### Automation loop

When setting up an automated or recurring wiki-build process, use this priority order for selecting work items each execution:

1. **Source ingestion** — check `raw/_queue.md` for pending sources; if any, ingest up to 2.
2. **Rebuild indices** — run all four maintenance scripts in order.
3. **Select up to 5 work items** by priority:
   - **Priority A**: high-demand red links (orphans with reference count >= 3) — write new concept.
   - **Priority B**: unused source claims (from `unused_claims.json`, prioritizing sources with lowest utilization %) — write new concept or enrich existing one.
   - **Priority C**: stub upgrades (concepts with `status: stub` and inbound links >= 2) — expand to draft.
   - **Priority D**: low-demand red links (orphans with reference count < 3) — write new concept.
4. **Execute** — write or update concept articles, following the wikilink policy so new articles generate 2–3 red links.
5. **Validate** — re-run all scripts; verify `check_links.py` exits 0 and `orphans.json` is NOT empty (if it is, the wikilink policy isn't being followed).

### Health metrics

| Metric | Healthy | Warning |
|---|---|---|
| `orphans.json` count | 5+ red links | 0 (frontier collapsed) |
| Unused claims utilization % | 30–70% per source | >95% (source fully mined) or <10% (not being used) |
| New red links generated per round | 3–10 | 0 (LLM too conservative) |
| `check_links.py` exit code | 0 | non-zero (hallucinated citation) |
| Ratio stub : draft : stable | Decreasing stubs over time | Stuck at mostly stubs |

The single most important metric is **"did this round generate new red links?"** If yes, the wiki is still growing. If no, either the wikilink policy isn't being followed or the wiki has genuinely covered its domain — which is fine, but only if unused-claims utilization is also high.

### When the wiki genuinely converges

A wiki reaches its natural size for the current source base when: `orphans.json` has only low-priority red links pointing outside the wiki's scope, `unused_claims.json` shows >90% utilization across all sources, most concepts are `draft` or `stable`, and new source ingestion produces updates rather than new concepts. Growth resumes when you ingest new sources.

## Bootstrapping a new wiki

When the user wants to start a fresh wiki, run the bundled bootstrap script:

```
python scripts/bootstrap_wiki.py <wiki-root>
```

This creates the directory tree, copies the three maintenance helpers into `<wiki-root>/scripts/` so the wiki is self-contained, scaffolds both an `AGENTS.md` (from `assets/AGENTS.template.md`) and an `index.md` portal page (from `assets/index.template.md`), and seeds empty indices. It refuses to run against a non-empty directory so it can't clobber existing work.

After bootstrapping, the first real task is to edit `AGENTS.md` together with the user. It is the canonical agent-instructions file for the wiki — read first by any AI session, regardless of which tool is running it — and contains both the operational retrieval protocol (lookup order, boundary discipline, post-edit script sequence; mostly the same across wikis) and the wiki-specific conventions (domain, controlled tag vocabulary, source-id convention, house rules) that the user customizes per project. The customization is what gives the file its value; un-edited convention sections defeat the purpose. The scaffolded `index.md` can be left mostly untouched until the wiki has enough concepts to make a portal worthwhile (~10 concepts).

If the bootstrap script is unavailable for some reason (e.g. the skill was partially installed), the fallback is the manual procedure: create the directories from the "Wiki layout" section, copy the three helper scripts into `<wiki-root>/scripts/`, write an `AGENTS.md`, write an `index.md` portal page at the wiki root, and run `build_alias_index.py` followed by `build_backlinks.py` once to seed the indices.

### Post-bootstrap setup: pre-commit hook (and retrofits)

`bootstrap_wiki.py` auto-creates the `CLAUDE.md` stub alongside `AGENTS.md`, so new wikis route Claude Code to the canonical `AGENTS.md` (and Anthropic's tooling thus picks up the same instructions ChatGPT/Codex/Cursor users get from `AGENTS.md`) without any manual step. The one remaining post-bootstrap step worth doing is wiring `check_links.py` into a git pre-commit hook so hallucinated citations are blocked before they enter the history. An optional `/wiki` slash command can also be added for explicit wiki-only Q&A, but it is mostly redundant once `CLAUDE.md` is in place. **See `references/llm_retrieval_setup.md` for the pre-commit hook template, the `/wiki` command template, and the rationale behind the stub-vs-symlink choice** — read that file especially when retrofitting an existing wiki that predates the canonical-`AGENTS.md` pattern (its `CLAUDE.md` will be a full retrieval-protocol copy that needs to be replaced with the stub, and its `AGENTS.md` will lack the operational sections).

## Common pitfalls

These are the failure modes that historically kill LLM-maintained wikis. Watch for them.

- **Hallucinated citations.** The LLM writes a plausible-looking `[[smith-2019-foo#^thm-1|Smith 2019, §thm-1]]` in a `## Notes` entry for a source that doesn't exist. `check_links.py` catches this, but only if it's actually run. Run it.
- **Lead bloat.** The lead grows from 2–4 sentences to a wall of text and stops being independently scannable. If a lead exceeds 5 sentences, refactor.
- **Folder creep.** Someone (you, probably) decides `concepts/ml/transformers/architecture.md` is a great idea. It is not. Keep `concepts/` flat. Use tags.
- **Manual backlinks.** Resist the urge to write "## See also" sections by hand. Let the index do it.
- **Source files that are full re-summaries.** A source file is an index, not a replacement for reading. If a source file is longer than the lead of the concept it supports, it's doing too much.
- **Tag drift.** Two months in you'll have `[ml]`, `[machine-learning]`, and `[ML]` all in use. Maintain a controlled vocabulary in `AGENTS.md` and grep for new tags before adding them.
- **Unicode math.** Writing `α` instead of `$\alpha$`, `P(X)` instead of `$P(X)$`, `≥` instead of `$\geq$`. Unicode math doesn't render in MathJax, drifts inconsistently, and defeats convention checking. Every piece of math — even a single variable name — must be in LaTeX inside `$...$` or `$$...$$` delimiters. This applies everywhere: concept articles, source files, portal pages, and tables.
- **Broken `$\sim$` for "approximately".** Writing `$\sim$3` (two adjacent math blocks) instead of `${\sim}3$` (one block). Obsidian's MathJax parser mis-reads the `$`-boundary when `$\sim$` is immediately followed by a number. Always merge into a single block: `${\sim}3$`, `${\sim}50$ km`.
- **Confusing "I have a wiki" with "I understand the field".** The wiki is a tool for retrieval and organization, not a substitute for reading the underlying material. Periodically read a concept article cold and check whether you can defend it from memory.

## What this skill does NOT do

- It does not auto-categorize or auto-tag without user oversight. Tag drift is one of the main ways wikis rot.
- It does not summarize entire papers into concept articles. Summaries go in source files; concept articles synthesize across sources.
- It does not delete or rewrite content without explicit user approval. If a concept article needs to be split or merged, ask first.
- It does not maintain a single canonical "tree of knowledge". Wikipedia doesn't either, for good reason.
