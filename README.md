# wiki-builder

A Claude Code skill for building and maintaining personal markdown knowledge bases from raw source material, inspired by Wikipedia's architecture (namespaces, lead-first articles, inline citations, aliases, disambiguation, derived backlinks).

## What this skill does

Turns a folder of raw sources (PDFs, articles, datasets) into a structured, navigable wiki that an LLM can retrieve from reliably. The design borrows the parts of Wikipedia's architecture that do useful work and drops what doesn't fit a single-author, LLM-assisted workflow.

Three guarantees the skill is built around:

1. **Faithfulness wins.** Every non-trivial claim has a citation pointing to a real file in `sources/`. Hallucinated citations are the main failure mode, and `check_links.py` is the line of defence.
2. **Lead-first articles.** Each concept opens with a 2–4 sentence independently-readable lead, bolded definition as the first sentence. This is what makes retrieval fast.
3. **Low-maintenance growth.** Backlinks are derived, not hand-maintained. Categorization uses tags in frontmatter, not folder hierarchy. Structure survives 10→1000 concepts without rework.

## Wiki layout

```
my-wiki/
├── AGENTS.md              # canonical agent instructions: retrieval protocol + wiki conventions
├── CLAUDE.md              # one-line stub routing Claude Code to AGENTS.md
├── index.md               # hand-maintained portal page
├── concepts/              # main namespace — one file per concept
├── sources/               # one file per ingested raw source
├── meta/                  # editorial notes, open questions
├── disambig/              # disambiguation pages
├── raw/                   # untouched original files (PDFs, HTML dumps)
├── scripts/               # four maintenance helpers
└── indices/               # generated by scripts — never hand-edit
    ├── aliases.json
    ├── backlinks.json
    ├── orphans.json
    └── unused_claims.json
```

## Installation

### As a user-level Claude Code skill (recommended)

Clone this repo into your user-level skills directory:

```bash
# Linux/macOS
git clone https://github.com/0u88/wiki-builder ~/.claude/skills/wiki-builder

# Windows (PowerShell)
git clone https://github.com/0u88/wiki-builder "$env:USERPROFILE\.claude\skills\wiki-builder"
```

After cloning, Claude Code will auto-detect the skill and make it available via the `Skill` tool in any directory.

### As a project-level skill

Clone into a specific project's `.claude/skills/` directory instead:

```bash
git clone https://github.com/0u88/wiki-builder <project-root>/.claude/skills/wiki-builder
```

## Usage

### Bootstrap a new wiki

```bash
python <skill-path>/scripts/bootstrap_wiki.py <wiki-root>
```

This creates the directory tree, copies the four maintenance scripts into `<wiki-root>/scripts/`, and scaffolds `AGENTS.md` and `index.md` from the bundled templates. After bootstrapping, edit `AGENTS.md` to record project-specific conventions (domain, tag vocabulary, source-id convention, wikilink policy).

### Ingest a source

In Claude Code, invoke the skill and ask it to ingest a PDF or article. The skill follows the standard workflow:

1. Place the raw file in `<wiki-root>/raw/`.
2. Write a `sources/<id>.md` file with a structured summary + 3–10 key claims, each with an Obsidian block-reference anchor.
3. For each concept the source touches, update the concept article (or create a stub if it doesn't exist) with inline footnote citations.
4. Run `check_links.py` to verify no hallucinated citations.
5. Rebuild indices.

### After any non-trivial edit

Run, in order:

```bash
python scripts/build_alias_index.py <wiki-root>
python scripts/build_backlinks.py <wiki-root>
python scripts/check_links.py <wiki-root>
python scripts/unused_claims.py <wiki-root>
```

`check_links.py` exits non-zero if any citation fails to resolve: a citation to a source file that does not exist, a `#^anchor` that does not exist inside the cited source file, or a `[^N]` footnote with no definition. The anchor check matters most: an LLM that hallucinates rarely invents a whole source, but it often attributes an invented claim to a real one. Wire it into a pre-commit hook if the wiki is git-tracked. `unused_claims.py` surfaces source block-ids that no concept article cites yet — the supply-side growth queue.

## Citation format

Citations use the Wikipedia / academic-paper convention: a numbered footnote reference in the body, with the actual source wikilink in a `## Notes` section at the bottom.

```markdown
… some non-trivial claim[^1]. Another claim using the same source[^1].
Something from a different source[^2].

## Notes

[^1]: [[angelopoulos-2023-ppi#^thm-1|Angelopoulos 2023, §thm-1]]
[^2]: [[zhu-2023-phasenet-das#^sec-methods|Zhu 2023, §sec-methods]]
```

`check_links.py` validates both halves of every `[[source-id#^anchor]]` wikilink: the source file must exist, and `^anchor` must be a block ID in that file's key claims. Per-file footnote numbering — each concept article restarts at `[^1]`.

## Math notation conventions

The bundled `references/math_conventions.md` and `references/math_examples.md` files establish a Wasserman-style (All of Statistics) LaTeX convention for mathematical notation, targeting Obsidian with MathJax 3. Key rules:

- All math in LaTeX (`$...$` or `$$...$$`), never Unicode — not even single Greek letters
- Vectors and matrices bold, transpose `^\top`
- `\operatorname*{arg\,max}` not `\arg\max`
- `\mathbb{P}` for event probabilities, `\mathbb{E}` for expectations
- Inline `1/2`, reserve `\frac` for display math

See `references/math_examples.md` for 10 worked golden-reference examples.

## Retrieval test framework

A three-tier stress test for verifying that an LLM can actually retrieve from the wiki:

- **Tier 1 — Lookup.** Basic "What is X?" questions. Verifies lead-first format and frontmatter parseability.
- **Tier 2 — Structural.** Multi-hop questions that require using indices, backlinks, and wikilinks. Exposes weak cross-referencing.
- **Tier 3 — Boundary.** Tests whether the wiki is actually the LLM's knowledge boundary — includes "I don't know" tests, contradiction tests, and fabricated-citation tests.

Full checklist in `references/test_checklist.md`.

## Sustainable growth

A wiki that relies solely on red links (`orphans.json`) for its growth queue will stall at 20–30 concepts — red links deplete as you resolve them, and an LLM asked to "keep things clean" stops generating new ones. The skill runs four complementary growth engines instead:

1. **Red links** (`orphans.json`) — concepts referenced but not yet written. Self-consuming; must be replenished by new concepts.
2. **Unused claims** (`unused_claims.json`) — source-file key claims with `^block-id` anchors that no concept article cites yet. Proportional to ingested sources; never depletes as long as new sources arrive. The supply-side growth queue.
3. **New source ingestion** (`raw/_queue.md`) — the fundamental fuel. Optionally maintain a queue file listing sources downloaded but not yet ingested; automated loops check it each run.
4. **Quality deepening** — upgrading `status: stub` articles to `draft` or `stable`, adding second-source perspectives, filling in meta decision logs. Prioritize stubs with high inbound-link counts.

**Wikilink policy**: a good concept article produces 3–8 outbound wikilinks, of which 2–3 may be red links to concepts not yet written. Zero red links means the wiki has stopped growing. Record this policy in each wiki's `AGENTS.md` so future and automated sessions follow it.

**Automation loop** (for scheduled or recurring builds): ingest any queued sources → rebuild all four indices → select up to 5 work items in priority order (A: high-demand red links with ≥3 inbound references, B: under-utilized source claims, C: stub upgrades with ≥2 inbound links, D: low-demand red links) → execute, following the wikilink policy so new articles generate 2–3 fresh red links → re-validate. See `SKILL.md` for the full framework.

**Health metrics** to track across rounds:

| Metric | Healthy | Warning |
|---|---|---|
| `orphans.json` count | 5+ red links | 0 (frontier collapsed) |
| Unused-claims utilization | 30–70% per source | >95% (fully mined) or <10% (unused) |
| New red links generated per round | 3–10 | 0 (LLM too conservative) |
| `check_links.py` exit code | 0 | non-zero (hallucinated citation) |
| Stub : draft : stable ratio | stubs decreasing | stuck at mostly stubs |

The single most important signal is **"did this round generate new red links?"** If yes, the wiki is still growing. If no, either the wikilink policy isn't being followed or the wiki has genuinely covered its domain — distinguish by checking unused-claims utilization.

## Example: a TabPFN research wiki

[`examples/tabpfn-wiki/`](examples/tabpfn-wiki/) is a real wiki built with this skill during a
research project on tabular foundation models and causal inference. Start at its portal page,
[`index.md`](examples/tabpfn-wiki/index.md).

| | |
|---|---|
| Sources ingested | 5 papers: PFNs (Müller 2022), TabPFN (Hollmann 2023), TabPFN v2 (Hollmann 2025, *Nature*), Do-PFN (Robertson 2025), CausalPFN (Balazadeh 2025) |
| Concept articles | 24, covering in-context learning, synthetic-data priors, structural causal models, strong ignorability, front-door/back-door criteria, and more |
| Citation check | `check_links.py`: 0 unresolved citations |
| Growth frontier | 54 red links to 6 not-yet-written concepts (e.g. `tabpfn`, `causalpfn`, `gaussian-process`) |

To verify it yourself:

```bash
python scripts/check_links.py examples/tabpfn-wiki
```

The original paper PDFs (`raw/`) are not redistributed. Each source file links to the public paper.

## Tests

```bash
pip install pytest
pytest
```

The tests build small wikis and check that `check_links.py` rejects a fabricated anchor in a real source, an unknown source, and a footnote without a definition. They also check that it accepts valid citations, red concept links and syntax examples in code, and that the example wiki passes.

## Design philosophy

The skill's philosophy, from SKILL.md:

> A wiki built this way has three jobs, in priority order:
>
> 1. **Faithful index of sources.** Every non-trivial claim must be traceable back to a specific source file. The wiki is not a place for the LLM to freelance — it is a place to organize what real sources actually say. Hallucinated content is worse than no content.
> 2. **High-density retrieval surface.** The user (and future LLM sessions) should land on any concept file and immediately get oriented. This is what the lead-first rule is for.
> 3. **Low-maintenance growth.** Structure must survive the wiki growing from 10 to 1000 files without manual rework. This is why backlinks are derived, categories are tags rather than folders, and the directory layout is deliberately shallow.
>
> When these three goals conflict, faithfulness wins.
